# 개발 안내

## 개발 환경

저장소 루트에서 Python 테스트를 실행한다.

```bash
.venv/bin/python -m pytest
```

프런트엔드 명령은 `frontend`에서 실행한다.

```bash
cd frontend
npm install
npm run build
npm run dev:graph-viewer
npm run dev:market-desk
```

MarketDesk 백엔드와 프런트엔드를 함께 띄우려면 저장소 루트에서 다음 스크립트를 실행한다.

```bash
./scripts/dev-market-desk.sh
```

Backend API의 기본 포트는 `8765`다. 공통 설정은 `src/finiq/config.py`에서 관리한다.

## 문서 확인

문서 도구를 설치하고 로컬 사이트를 실행한다.

```bash
.venv/bin/python -m pip install -e '.[docs]'
.venv/bin/mkdocs serve
```

배포와 같은 조건으로 검사하려면 strict build를 실행한다.

```bash
.venv/bin/mkdocs build --strict
```

## 문서 작성 규칙

### 정보 배치

단계 색인은 목적과 책임별 문서 안내만 둔다. 실행·검사·저장처럼 따로 조회하거나 변경하는 계약은 나누고, 하나의 상태 전이나 처리 순서로 함께 판단해야 하는 규칙은 한 문서에 유지한다.

- 생산 단계가 출력 형식을 소유한다. 소비 단계는 필요한 추가 조건만 적고 같은 형식을 다시 설명하지 않는다.
- 공통 규칙을 단계마다 복사하지 않는다.
- 한 계약은 한 파일만 소유한다. 색인이나 다른 문서에서는 계약을 다시 요약하지 않고 소유 문서의 역할만 안내한다.
- API와 저장 형식은 구현·테스트를 기준으로 삼고, 문서에는 필드의 의미와 사용 조건을 적는다.
- 영구 문서에는 테스트 통과 건수, 작업 인수인계, 임시 계획을 기록하지 않는다.
- 문서 경로를 옮기면 저장소 링크와 경로 검사도 함께 고친다.
- 관련 코드가 바뀌면 같은 PR에서 문서를 함께 검토한다.

### 한국어 문장 편집 기준

- 화면과 문서의 기능명·단계명은 [UI 용어 계약](design/terminology.md)을 따른다. 비슷한 표현을 새로 만들지 않는다.
- 앞 문장에서 범위를 제한했다면 뒤에서는 제외한 나머지를 포괄해 표현하고 하나씩 다시 열거하지 않는다.
- 문단 첫 문장이 이어지는 목록 전체의 기준이나 해석을 더하지 못하면 목록으로 바로 시작한다. 항목 하나만 미리 되풀이하지 않는다.
- 목록과 겹치는 요약은 전체 원리나 판단 기준을 알려 줄 때만 유지한다.
- 조건과 의미는 바꾸지 않으면서 번역투, 불필요한 피동 표현과 기계적인 문장 반복을 줄인다.

#### 범위 제한 예시

수정 전:

> 공통 디자인 시스템에 추가 계약이 필요한 컴포넌트만 이 폴더에 문서화한다. 색상, 타이포그래피, 공통 간격과 UI 용어는 상위 디자인 시스템을 따른다.

수정 후:

> 공통 디자인 시스템에 추가 계약이 필요한 컴포넌트만 이 폴더에 문서화한다. 기타 규칙과 용어는 상위 디자인 시스템을 따른다.

#### 부분 반복 예시

목록에서 기존 폴더를 확장하지 않는다고 설명한다면 도입부는 다음 문장으로 끝낸다.

> 연도별 처리는 요청 기간을 달력 연도 경계에서 나누는 방식이다.

`연도마다 하나의 고정 폴더를 유지하거나 앞선 폴더의 종료일을 늘리는 방식은 아니다`라는 문장은 목록 일부만 미리 반복하므로 쓰지 않는다.

### 기능 단계 분류

- 한 절에 서로 다른 기능 책임이 섞이면 입력, 검사, 판정, 복구와 표시처럼 실제 처리 순서대로 소제목을 나눈다.
- 같은 스키마의 필드나 한 번에 이어지는 추출 규칙은 한 목록으로 유지한다.
- 정상 흐름은 단계 본문에 적는다. 합리적인 다른 선택을 막거나 조건에 따라 방식을 바꾸는 규칙은 `제약과 분기`, 실행을 계속할 수 없는 조건은 `중단 조건`으로 구분한다.
- 값이 없을 때 사용하는 기본 동작은 `기본값`에만 적고 제약이나 실패 조건과 섞지 않는다.
- 내용이 없으면 파일도 만들지 않는다.

직렬 무결성 검사는 다음과 같이 실제 실행 순서로 구분한다.

```text
기존 데이터 무결성 검사
├─ 메타데이터 읽기
├─ 현재 설정과 비교
├─ 저장 파일 구성 검사
├─ KIND 건수 비교
├─ 검사 판정
├─ 정리와 재검사
└─ 결과 표시
```

### 설계 판단 기록

한 단계 안에서 끝나는 판단은 해당 문서의 `근거` 절에 적는다. ADR은 다음 조건을 모두 만족할 때만 작성한다.

1. 현실적인 대안이 둘 이상 있었다.
2. 선택에 중요한 비용이나 장단점이 있었다.
3. 영향이 여러 단계 또는 컴포넌트에 걸쳐 오래 지속된다.

버그 수정 이유는 PR, 향후 작업은 Issue나 `PLANS.md`, 운영 중 임시 조치는 운영 기록에 남긴다.

## 구현 검토

검토할 항목이 있으면 `PLANS.md`를 작업 대기열로 사용한다. 계약, 구현, 테스트를 함께 확인하고 오류가 없는 항목은 대기열에서 제거한다. 동작을 바꿨다면 관련 단계 문서와 UI 용어 계약도 같은 변경에서 맞춘다.
