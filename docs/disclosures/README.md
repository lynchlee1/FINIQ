### **1. Summary**

#### **기능 요약**
- 공시분석 단계별 문서와 담당 경로를 연결한다.
- 여러 단계가 함께 쓰는 작업공간, 저장 방식과 Web UI 규칙을 설명한다.
- 공시 처리 1~7단계를 차례로 실행하고 각 단계의 결과를 검증한다.

#### **세부 설명**
- 각 단계 문서는 그 단계에만 적용되는 규칙만 설명한다.
- 모든 행동은 [행동 분류 기준](../behavior-classification-rules.md)에 따라 `Layer → Behavior → Responsibility` 순서로 기록한다.
- Core는 같은 입력에서 만들어지는 데이터가 달라지는 규칙이고, Serving은 Core 결과를 바꾸지 않는 요청·실행·표시 규칙이다.
- 정상 입력에서의 선택·제외·빈 결과·대기는 Feature다. 예상하지 못한 실패 뒤 다른 값·방법·축소 범위로 계속할 때만 Fallback이며, 안전한 결과를 만들 수 없어 현재 실행을 끝낼 때만 Shutdown이다.
- 검증 규칙과 검증 실패 처리는 각각 Feature와 Fallback 또는 Shutdown으로 분리한다.
- Responsibility는 현재 작업에서 데이터가 맡는 역할로 정한다. 이전 단계의 결과도 현재 작업에서 읽어 사용할 때는 입력이며, 완성된 결과를 바꾸지 않고 유효성을 증명하는 manifest·metadata·완료 표식은 Result Validation이다.
- 한 규칙에는 입력 확정, 결과 생성, 완료 결과 검증 중 하나의 책임만 기록한다.

### **2. Core**

#### **Feature**

**[Result Validation] 단계 결과 게시 기능**

- **목적:** 완성된 단계 결과만 현재 결과 위치에 게시한다.
- 기존 결과를 백업한 뒤 새 단계 폴더를 `.automation-current` 위치로 옮긴다.
- 업무값을 바꾸지 않고 완료된 후보 결과의 게시 여부를 확정하는 단계이므로 Result Validation이다.
<br>

**[Result Validation] HTML 원본 metadata 연결 기능**

- **목적:** 저장한 HTML을 같은 `acpt_no`의 원본 공시와 연결해 manifest를 만든다.
- HTML 저장이 끝난 뒤 원본 JSON에서 같은 `acpt_no`의 공시를 찾아 manifest metadata로 사용한다.
- manifest는 저장된 HTML의 원본 연결을 증명하고 HTML 자체를 바꾸지 않으므로 Result Validation이다.
<br>

#### **Fallback**

- 없음.

#### **Shutdown**

**[Result Validation] 단계 결과 교체 실패시 실행 중단하기**
- **목적:** 새 결과로 교체하지 못하면 기존 결과를 복원하고 자동화를 중단한다.
- `os.replace`가 실패했을 때 `.automation-current`가 비어 있고 백업이 남아 있으면 백업을 원래 위치로 되돌린 뒤 실패 처리한다.
<br>

**[Result Validation] HTML 저장 연결 오류시 중단하기**
- **목적:** 저장한 HTML과 원본 공시를 연결할 수 없으면 manifest를 만들지 않는다.
- HTML 저장이 끝난 뒤 원본 JSON에서 같은 `acpt_no`의 공시를 찾지 못하면 요청 전체를 실패 처리한다.
<br>

### **3. Serving**

#### **Feature**

**[Core Processing] 단계별 자동화 실행 기능**

- **목적:** 선택한 공시 처리 단계를 정해진 순서와 입력으로 실행한다.
- 선택한 1~7단계를 번호 순서대로 실행한다. 입력, 결과와 저장 규칙은 각 단계 문서를 따른다.
- 단계가 끝나면 완료 기록을 남긴다.
- 처리할 공시가 0건이면 빈 결과를 정상 완료로 표시한다.
- 03단계부터 실행하는 계획은 저장된 `조건검색 프리셋`을 지정해야 한다. 자동화의 변환 유형·조건이 프리셋과 다르면 실행하지 않는다.
- 자동화의 03단계는 프리셋 정본의 완료·중단 결과와 검사 완료 위치를 다음 실행 입력으로 전달한다.
<br>

**[Core Processing] 사용자 판단 대기 기능**

- **목적:** 6단계에서 저장 규칙이 없는 목차를 발견하면 사용자가 판단할 때까지 후속 단계의 실행 요청을 보류한다.
- 저장 규칙이 없는 목차를 발견하면 `needs_review` 상태와 이미 끝난 단계의 결과를 반환한다.
- 저장 규칙이 없는 목차가 있거나 이전 검토 결과가 없으면 `unmatched_policy=needs_review`로 실행하고 빈 검토 목록에서 시작한다.
- 모든 목차를 판단하면 기존 규칙과 새 결정을 Core 입력으로 전달해 후속 실행을 시작한다.
- 저장 규칙이 없는 목차를 정상 규칙으로 `needs_review`에 두는 것이므로 Shutdown이 아니다.
<br>

**[Input Handling] 공통 작업공간 기능**

- **목적:** 모든 공시 단계가 같은 작업공간을 Core 입력으로 사용하게 한다.
- 화면의 `작업공간 디렉토리`를 `<data_root>`로 사용하고 각 단계의 표준 경로를 그 아래에서 찾는다.
- `저장 디렉토리 별도 설정하기`가 꺼져 있으면 표준 경로를 사용한다. 켜져 있으면 해당 화면에서 지정한 별도 경로를 사용한다.
<br>

**[Input Handling] 변환 유형별 결과 경로 분리 기능**

- **목적:** 다른 변환 유형의 결과가 서로 덮어쓰이지 않도록 단계별 입출력 경로를 정한다.
- 03단계 정본은 `03-filter/<workflow-name>.json`에 저장하고, 04단계 호환용 파생 결과와 04·05·07단계 결과는 `<mode>` 폴더를 나누어 저장한다.
- 03단계 정본에서 만든 mode별 파생 선택 결과는 04·05단계의 같은 mode 다운로드에 사용하고, 07단계 결과도 같은 mode 폴더에 저장한다.
<br>

**[Input Handling] 기존 HTML 재사용 기능**

- **목적:** 이미 저장된 유효한 KIND HTML은 같은 결과를 다시 요청하지 않고 재사용한다.
- 내용을 UTF-8로 읽고 `<html` 또는 `openDisclsViewer`가 있으면 기존 HTML로 인정한다.
- 판별 결과는 다운로드 방법만 바꾸고 Core가 요구하는 HTML 결과는 바꾸지 않으므로 Serving이다.
<br>

**[Core Processing] 자동화 표시 수 기능**
- 파일 문제는 종류별로 앞의 20개만 보여 준다.
- 자동화 화면은 서버가 보관한 진행 내역 중 최근 30줄만 보여 준다.
<br>

**[Core Processing] 진행·오류 표시 기능**
- **목적:** 화면에 너무 많은 내용을 한꺼번에 표시하지 않는다.
- 각 단계 문서가 정한 개수만 화면에 보여 주며 전체 개수와 성공·실패 판단은 줄이지 않는다.
<br>

**[Core Processing] 공통 작업 상태 표시 기능**
- **목적:** 여러 공시 화면에서 작업 상태를 같은 방법으로 보여 준다.
- 처음 받은 진행 내역은 최근 10줄을 보여 주고, 이후 받은 내용은 최근 80줄만 유지한다.
- 긴 파일 경로는 마지막 네 부분만 보여 주고 앞부분은 `.../`로 줄인다. 실제 경로는 바꾸지 않는다.
<br>

**[Core Processing] 저장된 작업 이어받기 기능**

- **목적:** 화면을 다시 열어도 실행 중인 작업을 계속 확인한다.
- 브라우저에 작업 ID가 남아 있으면 그 작업의 상태를 다시 확인한다.
<br>

**[Core Processing] 다운로드 취소 기능**
- **목적:** 다운로드를 취소해도 이미 저장한 파일은 남긴다.
- 04·05단계는 취소 전에 저장한 파일과 취소 상태를 반환한다.
<br>

**[Core Processing] 빈 값 표시 기능**
- **목적:** 빈 화면 칸을 쉽게 알아보게 한다.
- 빈 값은 `-`로 표시하고 숫자 `0`은 그대로 표시한다. 저장 결과는 바꾸지 않는다.
<br>

#### **Fallback**

**[Core Processing] 단계 결과 불일치 후 재실행 기능**

- **목적:** 완료 기록이나 결과 파일이 현재 상태와 다르면 해당 단계부터 Core 실행을 다시 요청한다.
- 불일치가 확인된 첫 단계부터 필요한 후속 단계를 번호 순서대로 다시 실행한다.
<br>

**[Input Handling] 기존 HTML 판별 복구 기능**

- **목적:** 기존 파일을 정상적으로 판별하지 못해도 다운로드 실행 자체는 계속한다.
- UTF-8 해석에 실패한 byte는 제외하고 나머지 내용으로 한 번 판별한다.
- 파일을 읽지 못하면 기존 HTML로 인정하지 않고 정상 다운로드 경로를 사용한다.
<br>

**[Input Handling] worker 기본값 기능**
- **목적:** CPU 수를 알 수 없어도 작업을 시작한다.
- CPU 수를 확인하지 못하면 worker를 1개 사용한다.
<br>

**[Input Handling] 브라우저 작업 정보 복구 기능**

- **목적:** 브라우저 저장 공간을 사용할 수 없어도 현재 화면의 작업 확인은 계속한다.
- 브라우저 저장 공간을 읽지 못하면 저장된 작업이 없는 것으로 본다. 저장 공간을 바꾸지 못해도 현재 작업 확인은 계속한다.
<br>

**[Core Processing] 실패 이유 대체 표시 기능**

- **목적:** 서버 응답에 실패 이유가 없어도 작업 실패 상태를 표시한다.
- 서버가 실패 이유를 보내지 않으면 `Job failed`를 표시한다.
- 화면에 표시할 값을 대체해 결과를 구성하므로 Core Processing이다.
<br>

**[Core Processing] 설정 저장 실패 후 화면 유지 기능**
- **목적:** 설정을 저장하지 못해도 현재 입력값을 화면에서 지우지 않는다.
- 화면에는 입력값이 남지만 서버 설정은 바뀌지 않을 수 있다.
<br>

#### **Shutdown**

**[Input Handling] 자동화 설정 오류시 중단하기**
- **목적:** 읽을 수 없는 자동화 설정을 임의로 고치지 않는다.
- 저장한 설정이 JSON이 아니거나 현재 형식이 아니면 화면을 열지 못한 것으로 처리한다.
<br>

**[Input Handling] 공통 설정 오류시 중단하기**
- **목적:** 읽지 못한 설정을 이전 값이나 임의의 값으로 대신하지 않는다.
- 공통 설정을 가져오지 못하면 실패 처리한다.
- worker 수가 양의 정수가 아니면 실패 처리한다.
- 저장 경로를 읽을 수 없거나 작업 기록 보존 시간이 양의 정수가 아니면 실패 처리한다.
