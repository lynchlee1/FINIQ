# 공시 처리 구조

공시분석은 원문을 한 번에 업무값으로 바꾸지 않는다. 단계마다 다시 살필 수 있는 중간 결과를 남겨 입력 오류가 다음 단계로 퍼지지 않게 막는다.

## 단계를 나눈 까닭

01단계는 KIND 조건검색 원문을 다운로드받는다. 02단계는 검색 결과를 연도별 SQLite로 바꾼다. 03단계는 같은 입력에 조건을 적용해 처리 대상을 고른다. 04단계는 공시 선택 화면을, 05단계는 공시 본문을 HTML로 저장한다. 06단계는 원문 목차에서 바꿀 범위를 고른다. 07단계는 선택한 HTML을 업무값으로 바꾼다. 08단계는 저장 결과를 읽어 정정 전후를 비교하고, 09단계는 공시 사이 관계를 그래프로 만든다.

이렇게 나누면 사용자는 원문, 선택 결과, 변환 결과를 따로 살필 수 있다. 한 단계 계약을 바꿀 때 다음 단계에서 다시 살필 범위도 뚜렷해진다.

## 원본과 파생 결과

각 단계에는 다음 단계가 읽는 원본이 하나뿐이다. 화면 표시값, 호환 입력, 조회 결과처럼 다시 만들 수 있는 자료는 파생 결과로 다룬다.

03단계 `<workflow-name>.json`은 조건과 실행 결과를 함께 담는 원본이다. `<mode>/filtered.json`은 04단계에 넘기는 파생 파일이다. 제목 후보 조회는 SQLite를 직접 읽으며 파일을 만들지 않는다.

## 결과 게시

새 결과는 다른 곳에서 모두 만든 뒤 검사한다. 검사를 마치면 기존 결과를 따로 두고 새 결과를 현재 위치로 옮긴다. 바꾸지 못하면 따로 둔 결과를 되돌리고 작업을 끝낸다.

이렇게 하면 사용자는 완성한 결과와 아직 만드는 결과를 섞어 읽지 않는다. 단계마다 쓰는 검사식과 멈추는 조건은 [공시분석 공통 사양](reference.md)에서 찾는다.

## 재사용과 다시 실행

완료 기록과 실제 결과가 처음 어긋나는 단계부터 다음 작업을 다시 실행한다. 앞 단계 결과를 다시 쓰려면 해당 단계 Reference가 정한 무결성 검사를 통과해야 한다.

HTML은 파일이 있다는 까닭만으로 다시 쓰지 않는다. manifest에 적은 바이트 수와 SHA-256이 현재 파일과 같아야 한다. 기준 해시가 없는 외부 파일을 믿을지는 사용자가 직접 정한다.

## 사람이 판단해야 하는 경계

06단계가 처음 보는 목차를 찾으면 다음 단계를 멈추고 `needs_review` 상태를 기록한다. 사용자가 모든 목차를 저장할지 뺄지 정한 뒤 작업을 잇는다.

자동화는 이 판단을 추측하지 않고 앞서 고른 값으로 채우지도 않는다. 원문 범위를 잘못 고르면 07단계 이후 모든 결과가 달라질 수 있기 때문이다.
