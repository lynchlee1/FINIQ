# 문서 작성 기준

### 목적

- 정확한 뜻을 유지하면서 문장을 쉽게 읽을 수 있도록 표현 원칙을 정한다.

### 원칙
- 쉬운 한국어로 충분히 설명할 수 있으면 전문용어를 쓰지 않는다.
- 명사를 길게 이어 붙이지 않는다. 누가 무엇을 읽고, 판단하고, 저장하는지 동사로 쓴다.
- 문맥상 알 수 있는 대상은 반복하지 않는다.
  - 날짜 범위가 검색 조건에 포함되면 두 항목을 따로 나열하지 않는다.
  - 절대 규칙 하나로 충분하면 금지 대상을 길게 나열하지 않는다.
- 코드 이름, JSON key, 함수 이름과 경로는 원래 철자를 유지하고 backtick으로 감싼다.
- 확정하지 않은 동작이나 저장 위치를 문서에서 새로 정하지 않는다.
- Explanation에서는 Markdown 표를 쓸 수 있다. 다른 문서에서는 대응 관계를 굵은 항목명과 짧은 문단으로 나눠 세로로 읽게 한다.

### 예시로 익히는 작성법

새 문서를 쓰거나 기존 문장을 고칠 때는 아래 예시에서 **고친 후**의 문장 구조와 판단 과정을 따른다. 예문의 낱말을 그대로 복사하기보다, 불필요한 정보를 덜어 내고 실제 동작을 분명한 동사로 설명하는 방식을 익힌다.

#### 1. 문맥상 당연한 말과 불필요한 용어를 덜어 낸다

**고치기 전**

> 이 page는 공시 검색 조건과 날짜 범위를 input으로 받아 연도 boundary로 나눈 KIND page body를 저장한다.

**고친 후**

> 현재 문서는 검색 조건을 입력받아 연도별로 나눈 KIND page body를 저장한다.

**판단 이유**

- `이 page`는 `현재 문서`로 바꾼다.
- 날짜 범위는 검색 조건에 포함되므로 따로 나열하지 않는다.
- `input으로 받아`는 `입력받아`로 붙여 쓴다.
- `연도 boundary로 나눈`은 뜻이 바로 드러나는 `연도별로 나눈`으로 바꾼다.

#### 2. 명사 묶음을 주어와 동사가 있는 문장으로 바꾼다

**고치기 전**

> 사채발행 결과 field status validation 및 warning 생성 기준을 설명한다.

**고친 후**

> 현재 문서는 사채발행 결과의 상태를 판단하고 안내를 남기는 기준을 설명한다.

**판단 이유**

- `field status validation`처럼 명사를 이어 붙이지 않는다.
- `판단하고`, `남기는`, `설명한다`처럼 실제 행동을 동사로 쓴다.
- JSON key를 가리키지 않는 `warning`은 문맥에 맞는 `안내`로 바꾼다.

#### 3. 코드 이름만 보존하고 나머지는 쉽게 쓴다

**고치기 전**

> `title` field의 canonical source는 `compressed-external-html.json.title`이며 empty value는 전달하지 않는다.

**고친 후**

> `title`은 `compressed-external-html.json.title`에서 읽고, 값이 있을 때만 전달한다.

**판단 이유**

- `title`과 파일 경로는 실제 코드 이름이므로 그대로 둔다.
- `field`, `canonical source`, `empty value`는 각각 문장 구조, `에서 읽고`, `값이 있을 때`로 풀어 쓴다.
- “무엇의 출처인가”보다 “어디에서 읽는가”를 바로 설명한다.

#### 4. 절대 규칙은 금지 대상을 나열하지 않고 한 문장으로 쓴다

**고치기 전**

> `filtered.json`, KIND HTML, 외부 HTML, `mainDoc`와 `doc_no`에서 `rcept_no`를 추정하지 않는다. 회사명이나 다른 metadata도 대체 연결 경로로 사용하지 않는다.

**고친 후**

> DART 식별자는 **절대로** 추정하지 않는다.

**판단 이유**

- 금지 대상을 나열하면 목록에 없는 원천은 허용된다는 오해가 생길 수 있다.
- 같은 금지 규칙을 여러 문장으로 반복하지 않는다.
- 예외가 없는 규칙은 적용 범위를 포함한 한 문장으로 끝낸다.

#### 5. 실패 조건을 임의의 대체 처리로 완화하지 않는다

**고치기 전**

> 일치하는 회사가 여러 개이면 정규화한 회사명 exact match로 후보를 줄인다.

**고친 후**

> 일치하는 회사가 하나가 아니면 전체 작업을 즉시 중지한다.

**판단 이유**

- 실제 계약이 중단이라면 더 자연스러워 보인다는 이유로 대체 처리를 만들지 않는다.
- “없음”과 “여러 개”를 `하나가 아니면`으로 묶어 같은 실패 조건을 반복하지 않는다.
- 오탐 가능성이 있는 판단은 문서 표현으로 정당화하지 않는다.

#### 6. 아직 정하지 않은 사항은 정하지 않았다고 쓴다

**고치기 전**

> 연결 결과는 접수 연도별 JSON 파일로 저장한다.

**고친 후**

> 연결 결과를 저장할 위치와 파일을 나누는 방법은 아직 정하지 않았다.

**판단 이유**

- 문서는 이미 합의한 동작을 설명하며, 빠진 설계를 대신 결정하지 않는다.
- 예정이나 추측을 현재 계약처럼 단정하지 않는다.
- 정확한 미정 상태가 그럴듯한 가상 경로보다 유용하다.

#### 7. 표 안에서는 열 제목이 알려 주는 말을 반복하지 않는다

**고치기 전**

> worker parameter input이 null 또는 blank인 경우 fallback default value로 CPU 수를 적용한다.

**고친 후**

> worker 값이 비어 있으면 CPU 수를 사용한다.

**판단 이유**

- 표의 `언제` 열에서는 `인 경우` 같은 안내를 덧붙이지 않아도 된다.
- `null 또는 blank`를 구분할 필요가 없으면 `비어 있으면`으로 묶는다.
- `fallback default value를 적용한다`보다 `1을 사용한다`가 짧고 분명하다.

#### 8. 구현 방법보다 사용자가 겪는 동작을 먼저 쓴다

**고치기 전**

> 04·05단계를 다시 실행할 때 기존 `.automation-current`에 이번 `filtered.json`의 같은 연도·`acpt_no`에 해당하는 유효한 HTML이 있으면 새 임시 결과 폴더에 먼저 하드 링크하고, 재사용하지 못한 대상만 내려받는다.

**고친 후**

> 이미 정상적으로 다운로드한 HTML은 다시 다운로드하지 않고 새 작업 폴더에서 재사용한다.

**판단 이유**

- 사용자는 파일을 재사용한다는 결과를 먼저 알아야 한다.
- `.automation-current`, `filtered.json`, `acpt_no`와 하드 링크는 이 문장에서 동작을 이해하는 데 필요하지 않다.
- 내부 구현은 계약을 구분하는 데 꼭 필요할 때만 별도로 설명한다.

#### 9. 여러 항목은 쓰임이 같은 것끼리 묶어 설명한다

**고치기 전**

> `compressed-external-html.json`에는 공시 식별값, 문서 번호·이름·순서·선택 상태, 필터 metadata, 외부 HTML의 byte 수와 SHA-256을 저장한다. 외부 HTML 전체, 화면 제어 요소, resource, script와 style은 압축 JSON에 저장하지 않고 연도별 원본 파일에 남긴다.

**고친 후**

> `compressed-external-html.json`에는 공시와 문서를 식별하고 문서 선택 결과를 재현하는 데 필요한 정보만 저장한다. 어떤 필터에서 선택됐는지 확인하는 정보도 함께 저장한다. 각 원본을 검증할 수 있도록 HTML의 바이트 수와 SHA-256을 기록한다. 원본 화면 전체는 압축 JSON에 복사하지 않고 연도별 HTML 파일로 보존한다.

**판단 이유**

- 여러 값을 쉼표로 이어 쓰지 않고 식별, 선택 결과 재현과 원본 검증이라는 쓰임으로 묶는다.
- 바이트 수와 SHA-256은 저장값 설명에서 분리해 무엇을 검증하는지 밝힌다.
- 제외할 HTML 요소를 하나씩 나열하지 않고 원본 화면 전체를 압축하지 않는다는 규칙으로 설명한다.

### 문장을 고치는 순서

1. 코드가 실제로 하는 일과 중단 조건을 먼저 확인한다.
2. 문맥상 당연하거나 앞에서 이미 말한 내용을 지운다.
3. 쉬운 한국어로 바꿀 수 있는 용어를 바꾼다.
4. 명사 묶음을 풀어 누가 무엇을 하는지 동사로 쓴다.
5. 코드 이름과 정확한 값만 backtick으로 보존한다.
6. 원래 동작을 빠뜨리거나 새로운 동작을 더하지 않았는지 대조한다.
7. 문장을 소리 내어 읽는다는 생각으로 조사, 호응과 불필요한 반복을 확인한다.

### 자주 바꿔 쓸 표현

**이 page:** `현재 문서`, `현재 화면`으로 쓴다. 실제 웹 화면을 다른 화면과 구분할 때만 원래 표현을 쓴다.

**input, output:** `읽는 값`, `저장 결과`, `입력값`, `결과`로 쓴다. API key나 함수 인자를 정확히 가리킬 때만 원래 표현을 쓴다.

**canonical:** `표준`으로 쓴다. 코드에 canonical이라는 구분이 실제로 있을 때만 원래 표현을 쓴다.

**boundary:** `범위`, `구분`, `규칙`으로 쓴다. 경계값처럼 다른 뜻으로 오해할 수 있을 때만 원래 표현을 쓴다.

**source:** `원본`, `원천`, `읽는 파일`로 쓴다. source code나 정확한 key 이름을 가리킬 때만 원래 표현을 쓴다.

**record:** `공시 한 건`, `결과 한 건`으로 쓴다. JSON 객체에서 정한 구조를 설명할 때만 원래 표현을 쓴다.

**payload:** `요청값`, `응답값`, `최종 결과`로 쓴다. API 또는 JSON 묶음 구조를 설명할 때만 원래 표현을 쓴다.

**field:** `값`, `항목`으로 쓴다. 실제 field 이름이나 field별 계약을 설명할 때만 원래 표현을 쓴다.

**table, row, cell, column:** `표`, `줄`, `칸`, `열`로 쓴다. HTML 요소나 parser 내부 자료형을 설명할 때만 원래 표현을 쓴다.

**directory, file:** `폴더`, `파일`로 쓴다. 코드 식별자나 기존 문서명에 들어갈 때만 원래 표현을 쓴다.

**workflow:** `처리 과정`, `작업`으로 쓴다. 여러 단계를 묶은 기능에서 정한 이름일 때만 원래 표현을 쓴다.

**stage:** `단계`로 쓴다. API 값이나 경로 이름을 정확히 가리킬 때만 원래 표현을 쓴다.

**status, warning, error:** `상태`, `안내`, `실패`로 쓴다. JSON key 또는 고정 code를 설명할 때만 원래 표현을 쓴다.

**fallback:** `대체 처리`로 쓴다. 코드에서 fallback 자체를 분류하거나 감사할 때만 원래 표현을 쓴다.

**mode:** `변환 유형`으로 쓴다. API 값이나 parser mode를 정확히 구분할 때만 원래 표현을 쓴다.

### 그대로 쓰는 이름

다음 이름은 화면과 코드에서 이미 정해져 있으므로 바꾸지 않는다.

**화면 변환 유형** — 사채발행파싱, 유무상증자파싱, 주주총회파싱, 유무형자산거래파싱, 발행증권거래파싱

**코드 용어** — parser, parsing, metadata, family, preview

**문서 안내** — 문서 목적, 다루지 않는 내용

`parser` 앞에 입력 형식을 덧붙인 결합 표현은 쓰지 않는다.

### Markdown 표기

#### backtick

- 코드 이름, JSON key·값, 함수, 경로와 코드 표현에 사용한다.
- 문자 단위로 정확히 일치해야 하는 원문이나 안내 문구에 사용한다.
- 일반 용어, 문서명과 단순 강조에는 사용하지 않는다.

#### 문서 링크

- 문서를 링크할 때 설명용 제목을 새로 만들지 않는다.
- 링크 문구에는 대상 파일명을 확장자까지 그대로 쓴다.
- 절을 직접 가리켜도 링크 문구는 파일명으로 두고, 필요한 절 이름은 링크 뒤 문장에 쓴다.

## 행동 분류 기준

### 목적

같은 시스템 행동을 문서마다 다르게 분류하지 않도록 공통 기준을 정한다. 행동의 조건과 결과를 확인한 뒤 다음 세 질문에 답해야 한다.

1. 업무 결과를 바꾸는가, 화면이나 API의 실행 방식을 정하는가?
2. 정상 조건에서 실행하는가, 예상하지 못한 실패 뒤에 실행하는가?
3. 입력 확정, 후보 결과 생성, 완료 결과 검증 가운데 어느 상태 변화를 직접 맡는가?

### 분류 순서

- 규칙 하나에는 기능 하나만 적는다.
- 각 행동을 **Layer → Behavior → Responsibility** 순서로 분류한다.

#### 2.1 Layer: Core · Serving

- **Layer**는 업무 결과를 만드는 과정과 사용자·API 상호작용을 나눈다.
- **Core**는 업무 입력을 받아 결과를 만들고 검사해 게시할 수 있는지 결정한다.
  - 어떤 업무값을 넣거나 뺄지, 완성한 후보 결과를 게시해도 되는지를 정하는 규칙이 여기에 속한다.
  - 규칙을 없앴을 때 업무 결과나 결과의 저장·게시 가능 상태가 달라진다면 Core다.
- **Serving**은 화면과 API가 Core 실행을 요청·조정하고 진행 상태와 결과를 보여 주는 방식을 정한다.
  - 요청이나 응답을 검사할 수는 있지만 문서가 정한 업무 결과를 만들거나 바꾸거나 인증하지 않는다.
  - 업무 결과와 유효성은 그대로이고 요청, 실행 제어, 표시만 달라진다면 Serving이다.
- Core와 Serving 안에서 행동을 다시 Feature, Fallback, Shutdown으로 나눈다.

#### 2.2 Behavior: Feature · Fallback · Shutdown

- **Behavior**는 정상 동작과 실패 뒤의 처리를 나눈다. 먼저 Feature인지 판단하고, Feature가 아닐 때만 Fallback과 Shutdown을 구분한다.
- **Feature**는 정상 입력과 자료를 처리하는 규칙이다. 값을 고르거나 거부하는 동작과 정상적인 빈 결과도 포함한다.
- **Fallback**은 예상하지 못한 실패 뒤에 다른 값·방법을 쓰거나 처리 범위를 줄여 현재 실행을 계속하는 규칙이다.
- **Shutdown**은 예상하지 못한 실패 때문에 안전한 결과를 만들 수 없어 현재 실행을 끝내는 규칙이다.

```text
정상 입력과 자료를 처리하는가?
├── 예: Feature
└── 아니요
    ├── 다른 방법이나 줄인 범위로 계속함: Fallback
    └── 안전한 결과를 만들 수 없어 끝냄: Shutdown
```

- 일부 항목을 뺐거나 실행을 끝냈다는 사실만으로 분류하지 않는다.
  - 정상 규칙에 따른 처리라면 Feature다.
  - 예상하지 못한 실패 뒤에도 실행을 계속할 때만 Fallback, 실행을 끝낼 때만 Shutdown이다.

#### 2.3 Responsibility: Input Handling · Core Processing · Result Validation

- **Responsibility**는 규칙이 현재 문서의 업무 결과와 어떤 관계인지 나타낸다.
  - 먼저 외부 입력, 업무 결과, 게시 경계를 정한다. 보조 함수 반환값, 화면 상태, 진행 내역, preview, 표시용 자료는 별도 업무 결과가 아니다.
- **Input Handling**은 업무 결과를 만들거나 바꾸지 않고 자료와 실행 상태를 받아들이고, 거부하고, 초기화하고, 준비한다.
  - 결과 생성을 시작하기 전에 입력을 읽고 찾고 해석하며, 입력의 존재 여부·형식·schema·필수값을 검사하는 과정이 여기에 속한다.
  - 기존 결과를 거부한 뒤 시작 범위를 고르는 동작도 Input Handling이다. Serving에서는 Core 실행 요청·전달·취소와 결과의 서식 변경·축약·표시도 포함한다.
  - 앞 작업의 결과 파일이나 Core 반환값을 다른 작업 또는 Serving이 읽으면 현재 규칙에서는 입력이다.
- **Core Processing**은 확정한 입력으로 업무 결과를 만들거나 결과의 값·구성원·관계·순서를 바꾼다.
  - 업무값 추출·선택·제외·계산·변환·집계·연결, 결과 구조 구성과 저장이 여기에 속한다.
  - Core Processing은 Core에서만 사용한다. Serving이 Core를 시작하거나 화면 응답을 만든다는 이유로 Core Processing이 되지는 않는다.
  - 후보 결과가 아직 완성되지 않았을 때 하는 검사는 결과에 무엇이 들어갈지를 정하거나 바꿀 때만 Core Processing이다.
- **Result Validation**은 완성한 후보 결과를 검사해 게시, 정상 저장, 반환, 재사용을 허용할지 정한다.
  - 결과의 구조·완전성·건수와 내부 또는 원본 일관성을 검사한다.
  - manifest, 검증 metadata, warning 기록, 완료 표식이 업무값을 만들거나 바꾸지 않고 완성 결과를 증명한다면 Result Validation이다.
  - 업무값을 고치고, 대신하고, 다시 계산하고, 걸러 내는 규칙은 Result Validation이 아니다.

```text
완성한 후보 결과를 바꾸지 않고 승인·거부·인증하는가?
├── 예: Result Validation
└── 아니요
    ├── 업무 결과를 만들거나 바꿈: Core Processing
    └── 결과를 바꾸지 않고 입력 확정·초기화·전달·제어·서식 변경·축약·표시를 맡음: Input Handling
```

### 경계를 판단하는 기준

- Core와 Serving은 어느 처리 과정을 맡는지로 나눈다.
  - 업무 결과를 만들거나 결과의 유효성과 게시 가능 상태를 정하면 Core다.
  - 작업을 요청·조정하고 상호작용 응답을 검사하거나 보여 주면 Serving이다.
- Feature와 Fallback은 다른 값을 고르는 일이 정상 처리에 속하는지로 나눈다.
  - 미리 정한 순서에 따라 값을 고르면 Feature다.
  - 원래 쓰려던 값이 실패해서 다른 값을 쓰면 Fallback이다.
- Feature와 Shutdown은 실행을 끝낸 까닭으로 나눈다.
  - 정상 규칙에 따라 입력을 거부하면 Feature다.
  - 예상하지 못한 실패 때문에 실행을 끝내면 Shutdown이다.
- 검증 규칙과 검증 실패 처리는 나누어 적는다.
  - 정상 처리에서 하는 검증은 Feature다.
  - 검증 실패 뒤 결과 범위를 줄여 계속하면 Fallback이다.
  - 검증 실패 뒤 실행을 끝내면 Shutdown이다.
- 항목을 뺐다는 사실만으로 분류하지 않는다.
  - 정상 규칙에 따라 항목을 빼면 Feature다.
  - 처리에 실패한 항목을 빼고 나머지를 계속 처리하면 Fallback이다.
- Responsibility는 파일 이름이나 앞 작업에서 맡았던 역할이 아니라, 현재 문서가 정한 업무 결과와 자료의 관계로 판단한다.
  - 저장된 이전 결과를 현재 입력으로 다시 쓰기 전에 검사하면 Input Handling이다.
  - 새 후보 결과를 게시하기 직전에 검사하면 Result Validation이다.
- 업무 결과는 보조 함수나 화면 구성 요소가 아닌 문서 경계에서 정한다.
  - Core 결과의 서식을 바꾸고 줄여 표시하는 일은 화면 상태를 만들더라도 Serving Input Handling이다.
  - Serving에서 Core를 시작·재시도·취소·감시하는 일은 Input Handling이다. 그 결과 업무값이 바뀐다면 별도 Core 규칙으로 적는다.
  - Serving에는 Core Processing을 사용하지 않는다.
- 복구를 시작하는 규칙과 실제 업무 처리는 나누어 적는다.
  - 유효하지 않은 이전 결과를 거부하고 전체 재처리 범위를 고르는 일은 Input Handling이다.
  - 대체 업무 결과를 만드는 정상 처리는 그대로 Core Processing이다.
- 파일을 만든다는 사실만으로 Responsibility를 정하지 않는다.
  - 업무값을 만들거나 바꾸면 Core Processing이다.
  - 완성 결과를 바꾸지 않고 증명하는 manifest, 검증 metadata, warning 기록, 완료 표식은 Result Validation이다.
- `read`, `check`, `validate`, `save`, `metadata`, `result`라는 낱말만 보고 Responsibility를 정하지 않는다. 실제 상태 변화를 확인한다.
- 규칙 하나에 둘 이상의 Responsibility 변화를 섞지 않는다.
  - 입력 확정, 결과 생성, 완료 결과 검증을 별도 규칙으로 나눈다.
  - 검증 실패 감지, 사용자 확인, 대체 결과 생성을 한 규칙에 함께 쓰지 않는다.
- 규칙마다 경계를 확인할 수 있어야 한다. 어떤 입력을 받는지, 어떤 업무 결과나 후보를 다루는지, 후보가 완성 전인지 완성 뒤인지 밝힌다.

### 작성 예시

아래 예시는 Layer, Behavior, Responsibility를 조합하는 방법을 보여 준다. Serving은 업무 결과를 바꾸지 않으므로 Core Processing 예시가 없다. 실제 문서에는 존재하는 규칙만 적고, 공시 문서에서 빈 분류는 `없음`으로 밝힌다.

```markdown
#### Core

##### Feature

**[Input Handling] 날짜 범위 확인**
- 시작일이 종료일보다 빠르거나 같은 범위만 입력으로 받는다.

**[Core Processing] 기간별 결과 선택**
- 확정한 날짜 범위에 들어오는 결과를 고른다.

**[Result Validation] 결과 건수 인증**
- 결과를 모두 고른 뒤 보고 건수와 실제 결과 건수가 같은지 확인하고, 결과를 바꾸지 않은 채 완료 표식을 기록한다.

##### Fallback

**[Input Handling] 이전 입력 형식 읽기**
- 현재 형식을 읽지 못하면 지원하는 이전 형식으로 같은 입력을 읽는다.

**[Core Processing] 실패 항목 제외**
- 처리하지 못한 항목을 빼고 나머지 항목으로 결과를 계속 만든다.

**[Result Validation] 다른 검사로 결과 인증**
- 기본 완료 검사를 실행하지 못하면 후보 결과를 바꾸지 않는 독립 검사를 사용한다.

##### Shutdown

**[Input Handling] 읽을 수 없는 입력 거부**
- 필수 입력 파일을 읽지 못하면 결과를 만들기 전에 작업을 끝낸다.

**[Core Processing] 결과 생성 실패**
- 처리 실패로 완성 결과를 만들 수 없으면 작업을 끝낸다.

**[Result Validation] 잘못된 결과 거부**
- 보고 건수와 실제 결과 건수가 다르면 저장하지 않고 작업을 끝낸다.

#### Serving

##### Feature

**[Input Handling] 요청값 변환**
- 요청값을 Core가 받는 입력 형식으로 바꾼다.

**[Input Handling] 결과 표시**
- 완료된 Core 결과를 바꾸지 않고 화면에 맞게 서식을 바꾸거나 줄여 보여 준다.

**[Result Validation] 응답 일관성 확인**
- 완료 응답을 반환하기 전에 Core 결과와 같은지 확인한다.

##### Fallback

**[Input Handling] 다른 위치에서 요청 읽기**
- 요청 본문을 읽지 못하면 query parameter에서 같은 요청값을 읽는다.

**[Input Handling] 일부 preview 표시**
- 일부 항목을 불러오지 못하면 확인한 preview 항목만 보여 준다.

**[Result Validation] 다른 검사로 응답 인증**
- 기본 완료 응답 검사를 실행하지 못하면 응답값을 바꾸지 않는 독립 검사를 사용한다.

##### Shutdown

**[Input Handling] 잘못된 요청 거부**
- 필수 요청값이 없으면 요청을 거부한다.

**[Input Handling] 실행 요청 실패**
- Core 작업을 시작하지 못하면 요청을 끝낸다.

**[Result Validation] 잘못된 응답 거부**
- 응답을 요청한 작업과 연결할 수 없으면 결과를 반환하지 않는다.
```
