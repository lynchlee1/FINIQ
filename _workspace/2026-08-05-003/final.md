# 공시 처리 구조

공시분석은 원문을 한 번에 업무값으로 바꾸지 않는다. 중간 결과를 단계마다 남기면 문제가 생긴 지점부터 다시 살필 수 있고 입력 오류가 뒤 단계로 퍼지는 범위도 줄어든다. 단계별 입출력은 [reference.md](reference.md)와 각 단계 Reference에서 확인한다.

## 단계를 나눈 까닭

사용자는 원문, 선택 결과와 변환 결과를 따로 살펴야 한다. 단계가 나뉘어 있으면 한 단계의 계약을 바꿨을 때 어떤 결과를 다시 검사해야 하는지도 분명해진다.

## 원본과 파생 결과

원본을 하나로 정하면 같은 작업을 다시 실행해도 출발점이 흔들리지 않는다. 화면 표시값이나 조회 결과처럼 다시 만들 수 있는 자료를 파생 결과로 다루는 이유도 여기에 있다. 어떤 파일이 원본이고 파생 결과인지는 각 단계 Reference에서 정한다.

## 결과 게시

완성한 결과와 아직 만드는 결과가 섞이면 사용자는 어느 쪽이 유효한지 알기 어렵다. 결과 게시와 복원을 분리한 까닭이다. 정확한 조건은 [reference.md](reference.md)에서 정한다.

## 재사용과 다시 실행

검증된 결과를 다시 쓰면 불필요한 다운로드와 변환을 줄일 수 있다. 반대로 완료 기록만 믿으면 손상되거나 달라진 결과를 정상 입력으로 넘길 수 있다. 재사용과 다시 실행의 정확한 조건은 [reference.md](reference.md)와 단계별 Reference에서 정한다.

## 사람이 판단해야 하는 경계

원문에서 어디까지 업무값으로 바꿀지는 사람의 판단이 필요한 경우가 있다. 자동화가 이전 선택을 새 원문에 적용하면 잘못된 범위가 뒤 결과 전체에 영향을 줄 수 있다. 판단을 요청하고 작업을 잇는 방법은 [guides.md](../06-html-section-split/guides.md), 정확한 중단 조건은 [reference.md](../06-html-section-split/reference.md)에서 확인한다.

# Ontology 처리 구조

Ontology 화면은 공시 단계 결과와 주가 자료를 함께 읽는다. 공시 원문을 다시 처리하지 않고 검증을 마친 결과를 입력으로 삼아 분석과 원본 처리의 책임을 나눈다.

## 자료를 합치는 원칙

여러 입력에서 같은 회사를 찾았을 때 병합 순서를 고정하면 값이 충돌해도 결과가 실행할 때마다 달라지지 않는다. 정확한 우선순위와 중복 처리 규칙은 [reference.md](reference.md)에서 정한다.

## Cache를 다시 만드는 까닭

Cache는 같은 입력을 다시 처리하는 비용을 줄이지만 오래된 cache를 읽으면 빠진 공시나 이전 회사 정보가 정상 결과처럼 보일 수 있다. 그래서 cache를 쓰지 못하는 상황과 업무값을 다른 원천에서 채우는 상황을 구분한다. 재사용 조건은 [reference.md](reference.md)에서 확인한다.

## 병렬 처리와 직렬 복구

병렬 처리는 시간을 줄이기 위한 실행 방법일 뿐 결과의 범위나 산식을 바꾸지 않는다. 병렬 실행을 시작할 수 없는 환경에서도 같은 결과를 만들 수 있도록 직렬 실행을 둔다. 적용 조건은 [reference.md](reference.md)에서 정한다.

## 불완전한 입력

입력 일부가 빠진 분석 결과는 전체 자료로 오해하기 쉽다. 그래서 불완전한 입력을 조용히 줄여 읽는 대신, 기능별 Reference가 입력 우선순위와 중단 조건을 명시한다.
