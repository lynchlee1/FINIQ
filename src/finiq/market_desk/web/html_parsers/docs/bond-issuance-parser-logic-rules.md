# 사채발행 파서 로직 규칙

작성일: 2026-07-06
최종 업데이트: 2026-07-11

HTML parsing 동작은
[HTML 파서 공통 로직 규칙](./common/common-html-parser-logic-rules.md)을 따르고,
공통 table, base record, 저장 payload의 필드 구조는
[HTML 파서 공통 데이터 구조](./common/common-html-parser-data-structure.md)를 따른다.
공통 상태, 경고, 실행 오류 처리는
[HTML 파서 공통 예외 처리 규칙](./common/common-html-parser-exception-handling.md)을 따른다.
외부 metadata의 위치와 필드별 Only SoT는
[외부 메타데이터 병합 규칙](./external-metadata.md)을 따른다.

이 문서에서 parser는 HTML에서 필요한 값을 읽는 프로그램이고, parsing은 그 프로그램이 값을 읽어 결과로 바꾸는 과정을 뜻한다.
table은 표, row는 표의 가로줄, cell은 표의 한 칸, column은 표의 세로줄, label은 `납입일`과 같은 항목 이름을 뜻한다.
record는 HTML 파일 한 건의 parsing 결과이고, `raw_tables`는 그 HTML의 모든 table을 담은 목록이다.
`logical_rows`는 빈 칸과 연속 중복을 줄여 검색하기 쉽게 만든 row이고, `positional_rows`는 실제 column 위치를 유지한 row이다.
workflow는 여러 record를 모아 저장하는 처리 과정, payload는 그 과정이 만든 최종 결과 묶음을 뜻한다.
base record는 개별 parser가 값을 더하기 전의 공통 기본 결과, metadata는 HTML 밖에서 더하는 정보, Only SoT는 해당 값을 가져오는 유일한 기준 출처, `null`은 저장할 값이 없다는 표시이다.
`parsed`는 정해진 위치에서 값을 읽은 상태, `explicit_zero`는 값을 읽을 표나 칸에서 0 또는 `-`를 확인한 상태, `source_not_found`는 정해진 출처에서 사용할 수 있는 값을 찾지 못한 상태이다.

### 처리 흐름
1. **공통 구조 생성**
- `build_base_record()`로 파일명 전체에서 만든 `acpt_no`와 모든 `raw_tables`를 만든다.
- parser는 전달받은 HTML만 읽으며 다른 HTML 본문을 찾아 바꾸지 않는다.
  - 의도 : 어떤 HTML을 읽었는지 입력 단계에서 확정한다.
2. **메인 table 선택**
- 메인 table의 `logical_rows`를 선택한다.
- 메인 table이 없으면 빈 row 목록을 유지한다.
  - 의도 : 이후의 기본 필드가 한 table 안에서만 추출되도록 범위를 고정한다.
3. **title 고정**
- 전달받은 `title`을 문자열로 바꾸고 앞뒤 공백만 제거해 record에 저장하고 종류 판정에 사용한다.
- 전달받지 못하면 빈 문자열을 유지한다.
- HTML 본문의 제목이나 사채 종류 문구로 `title`을 채우지 않는다.
  - 의도 : `title`의 출처를 외부에서 주입된 값 하나로 제한한다.
4. **필드 추출**
- 메인 table에서 사채 기본 필드를, 별도 투자자 table에서 투자자 목록을 추출하면서 각 항목의 `field_parse_status`와 원천 누락 경고를 바로 기록한다.
  - 의도 : 사채 조건과 투자자 상세 내역을 서로 다른 표 구조에 맞춰 읽고, 그때 확인한 원천 존재 여부를 잃지 않는다.
5. **관계 검증**
- 모든 항목을 추출한 뒤 발행목적·투자자 합계와 발행금액의 관계를 검증한다.
- 후처리는 상태를 다시 판단하거나 원천 table을 다시 검색하지 않는다.
  - 의도 : 원문 한 곳에서 결정하는 상태와 여러 추출값이 필요한 관계 검증을 구분한다.
6. **직접 반환**
- 사채 parser는 공통 `acpt_no`, `mode`, `title`, `상장구분`, `raw_tables`와 사채 업무 필드·상태·경고를 반환한다.
- 사채 parser는 `source_file`, `raw_rows`, `correction_families`, `rcept_no`를 반환하지 않는다.
- 저장 workflow는 `raw_tables`를 제거한 뒤 외부 metadata와 family 참조를 연결한다.
  - 의도 : 직접 parser 반환 구조와 저장 workflow가 담당하는 필드를 확정한다.

### 출력 필드
1. **사채 parser 필드**
- 모든 사채 종류는 같은 최상위 필드 구조를 사용한다.
- 식별자와 원문 table 같은 공통 필드는 공통 데이터 구조 문서에 따르고, 회사명·상장구분 같은 외부 필드는 외부 메타데이터 문서에 따른다.

| 필드 | 값 형식 | 값이 없을 때 |
|---|---|---|
| `mode` | `bond_issuance` | 고정값 |
| `title` | 전달받은 제목의 앞뒤 공백을 제거한 문자열 | 빈 문자열 |
| `회차` | 문자열 | `null` |
| `종류` | `BW`, `EB`, `CB` | `null` |
| `기업명(행사대상)` | 공백을 정리한 행사대상 문구 | `null` |
| `발행금액` | 정수 | `null` 또는 명시적 0 |
| `발행목적` | `[[목적명, 금액], ...]` | 원천 누락은 `null`, 명시적 0은 빈 목록 |
| `행사가액` | 정수 또는 실수 | `null` |
| `납입일` | 공백을 정리한 원문 cell text | `null` |
| `만기일` | 공백을 정리한 원문 cell text | `null` |
| `사채발행방법` | 공백을 정리한 원문 cell text | `null` |
| `행사시작일` | 공백을 정리한 원문 cell text | `null` |
| `행사종료일` | 공백을 정리한 원문 cell text | `null` |
| `투자자` | `[[대상자명, 발행권면총액], ...]` | 원천 누락은 `null` |

  - 의도 : CB·EB·BW를 같은 자료 구조로 제공해 다음 단계가 사채 종류마다 다른 필드 이름을 처리하지 않게 한다.

### table 선택 규칙
1. **메인 table**
- table 안의 어느 row에서든 `사채의 종류`, `사채의 권면`, `자금조달의 목적`을 각각 찾을 수 있는 첫 번째 table을 선택한다.
- label 검색과 필드 추출에는 빈 cell과 연속된 중복 cell을 제거한 `logical_rows`만 사용한다.
- 조건을 만족하는 table이 없으면 빈 row 목록으로 추출을 계속하고 strong 경고를 만든다.
  - 의도 : 여러 table의 행을 섞지 않고 하나의 사채 발행 조건 table 안에서만 기본 필드를 읽는다.
2. **특정인 대상 투자자 table**
- `logical_rows`의 첫 row에 `발행 대상자명`과 `발행권면`이 모두 있는 table만 후보로 본다.
- 실제 머리글의 열 위치와 값은 빈 cell과 반복 cell의 위치를 유지한 `positional_rows`에서 읽는다.
- `발행 대상자명` column과 `발행권면` column을 모두 찾고 두 위치가 다를 때만 유효한 후보로 인정한다.
- 유효한 후보가 여러 개여도 첫 번째 table만 처리하고 후속 table과 합치지 않는다.
  - 의도 : 표인지 확인할 때는 읽기 쉬운 행을 쓰고, 실제 값은 원래 열 위치에서만 가져온다.

### 필드 추출 규칙
1. **사채 종류**
- 주입된 `title`에서 `신주인수권부사채` → `교환사채` → `전환사채` 순서로 확인해 `BW` → `EB` → `CB`로 반환한다.
- 한 제목에 문구가 여러 개이면 먼저 확인한 종류를 사용한다.
- 본문 종류값으로 판정 결과를 보완하지 않는다.
  - 의도 : 종류 판정의 출처와 충돌 시 우선순위를 하나로 고정한다.
2. **회차와 단일 값 필드**
- `회차`는 `사채의 종류`를 포함하는 첫 row에서 정확히 `회차`인 cell의 바로 오른쪽 값을 읽는다.
- `납입일`은 cell과 label의 공백을 제거한 뒤 맨 앞의 `숫자.` 또는 `숫자-숫자.`만 제거했을 때 정확히 `납입일`인 cell이 있는 첫 row의 마지막 값을 읽는다.
- `만기일`은 `사채만기일`을 포함하는 첫 row를 사용하고, 없으면 `사채만기`를 포함하는 첫 row의 마지막 값을 사용한다.
- `사채발행방법`은 해당 문구를 포함하는 첫 row의 마지막 값을 사용한다.
  - 의도 : 각 필드의 label 범위와 기존 대체 label을 명시적으로 제한한다.
3. **발행금액**
- `사채의 권면`을 포함하는 row들을 모은 뒤 `원화기준`을 포함한 첫 row를 우선한다.
- `원화기준` row가 없으면 첫 번째 권면 row를 사용한다.
- 선택한 row의 첫 cell을 제외하고 오른쪽부터 확인해 처음 정수로 parsing되는 cell을 사용한다.
- 오른쪽부터 확인하는 중 `-`를 만나면 명시적인 0으로 기록한다.
  - 의도 : 해외발행에서도 원화 환산 권면액을 우선하고, 선택한 row 밖의 숫자는 사용하지 않는다.
4. **기업명 또는 행사대상 주식**
- 아래 label 순서로 각 row의 label cell 바로 오른쪽 값을 먼저 확인하고, 같은 cell 내부의 `종류:` 또는 `유가증권:` 형식을 이어서 확인한다.

  `전환대상` → `교환대상` → `인수권행사대상` → `전환에 따라` → `교환에 따라` → `인수권행사에 따라` → `전환으로 발행할` → `교환으로 발행할` → `인수권행사로 발행할`

- 이름에 `대상`이 있는 label은 label cell이 정확히 일치하거나 `종류`·`유가증권`을 함께 포함할 때 바로 오른쪽 값을 읽고, 같은 cell 내부에서는 `종류:` 또는 `유가증권:` 뒤를 읽는다.
- 이름에 `대상`이 없는 label은 label cell에 `종류`가 함께 있을 때 바로 오른쪽 값을 읽고, 같은 cell 내부에서는 `종류:` 뒤를 읽는다.
- 같은 cell 내부에서 읽을 때는 label과 `종류` 또는 `유가증권` 사이가 40자 이내이고 뒤에 `:` 또는 `：`가 있어야 한다.
- 같은 cell에서 뽑은 값은 코드가 `(1)`, `1)`, `1. `, `가.`, `①`처럼 알아보는 다음 번호 항목이 시작되기 전까지만 남긴다.
- 남은 값 양끝의 공백과 `.`, `;`, `:`, `：`, `-`, `/`를 제거한다. 정리한 값이 120자를 넘으면 사용하지 않는다.
- 위 경로에서 값을 찾지 못하면 이름에 `대상`이 없는 label에 한해 label 다음 cell이 정확히 `종류`일 때 그 다음 cell을 사용한다.
- 추출한 값에서 법인 형태나 주식 종류 표현을 제거하지 않는다.
  - 의도 : 알려진 사채 양식만 순서대로 지원하면서 원문 대상명을 임의로 정제하지 않는다.
5. **행사가액**
- `전환가액` → `교환가액` → `행사가액` → `전환가격` → `교환가격` → `행사가격` 순서로 확인한다.
- label cell에 `결정방법`, `조정`, `한도`가 포함되면 설명 row로 보고 제외한다.
- label 오른쪽 cell을 오른쪽부터 확인하고, 부호 없는 숫자·공백·쉼표·소수점과 선택적인 `(원)`, `(원/주)`, `원`, `원/주` 단위만 있는 값을 사용한다.
- 정수 모양이면 정수로, 소수점이 있으면 실수로 저장한다.
  - 의도 : 가격 설명 문장의 비율이나 예시 숫자를 행사가액으로 오인하지 않는다.
6. **행사기간**
- `전환청구기간` → `교환청구기간` → `권리행사기간` → `행사기간` 순서로 확인한다.
- 각 기간 row에서 `시작일` 또는 `종료일`을 함께 포함하는 첫 row의 마지막 값을 반환한다.
  - 의도 : CB·EB·BW 양식의 기간 label 차이만 제한적으로 허용한다.
7. **자금조달 목적**
- `자금조달의 목적`을 포함하는 각 row에서 해당 label 바로 다음 cell을 목적명으로 사용한다.
- 목적명에서는 `(원)`, 끝의 `원`, 양끝의 공백과 `-`, `_`, `/`, `·`, `,`만 제거하고 나머지 원문을 보존한다.
- 목적명 오른쪽에 남은 cell을 오른쪽부터 확인해 처음 정수로 parsing되는 값을 사용한다.
- 금액이 0이면 결과 목록에는 넣지 않지만 금액 원천은 존재한 것으로 기록한다.
  - 의도 : 목적명과 금액의 상대 위치를 고정하면서 0원 목적은 목록에서 제외한다.
8. **투자자**
- 대상자명은 선언된 `발행 대상자명` column에서만 읽고, 빈 값·`-`·`합계`·`총계`·`계`는 제외한다.
- 금액은 선언된 `발행권면` column에서만 읽는다.
- 대상자명이 있고 금액 cell이 `-`이면 해당 대상자를 `[대상자명, 0]`으로 보존한다.
- 금액 cell이 없거나 비어 있으면 사용할 값을 찾지 못한 것으로 처리한다.
- 금액을 숫자로 바꿀 수 없는 다른 글이면 해당 row를 제외한다.
  - 의도 : 대상자명과 금액 column을 독립적으로 고정하고 다른 column의 숫자를 대신 사용하지 않는다.

### 상태와 경고
1. **필드 상태 판정**
- 상태의 뜻, 저장값, 경고 수준, 검증 제외 규칙은 [HTML 파서 공통 예외 처리 규칙](./common/common-html-parser-exception-handling.md)을 따른다.
- 아래 표는 사채 parser가 각 필드에 상태를 적용하는 조건만 정한다.
- `field_parse_status`는 `회차`, `종류`, `기업명(행사대상)`, `발행금액`, `발행목적`, `행사가액`, `납입일`, `만기일`, `사채발행방법`, `행사시작일`, `행사종료일`, `투자자`의 12개 필드에 생성한다.

| 필드 구분 | `parsed` | `explicit_zero` | `source_not_found` |
|---|---|---|---|
| `발행금액` | 0이 아닌 숫자를 읽음 | 0 또는 `-`를 읽음 | 숫자 원천을 찾지 못함 |
| `발행목적` | 보존할 목적과 금액이 있음 | 0 또는 `-`인 금액 원천만 있음 | 금액 원천을 찾지 못함 |
| `투자자` | 보존할 투자자와 금액이 있음 | 사용하지 않음 | 유효한 투자자 값을 찾지 못함 |
| 나머지 필드 | 정해진 위치에서 값을 읽음 | 사용하지 않음 | 정해진 위치에서 값을 찾지 못함 |

- 나머지 문자열 필드에서 원문 `-`는 값이 존재하므로 `parsed`로 기록한다.
  - 의도 : 원천 존재 여부가 필요한 목록 필드와 단순 값 필드의 상태 판정을 구분한다.
2. **strong warning**
- 메인 table이 없으면 메인 table 누락 경고를 만든다.
- `source_not_found` 경고는 공통 예외 처리 규칙을 그대로 적용한다.
- 주입 제목이 없으면 `주입 제목이 없습니다.`를 별도로 추가한다. 이때 `종류`의 원천 누락 경고도 함께 생길 수 있다.
  - 의도 : 전체 구조 누락, 필드 누락, 제목 누락을 각각 확인할 수 있게 한다.
3. **weak warning**
- `발행목적` 목록이 비어 있지 않고 `발행금액`이 `null`이 아니면 목적 금액 합계를 정확히 비교한다.
- `투자자` 목록이 비어 있지 않고 `발행금액`이 `null`이 아니면 발행권면총액 합계를 정확히 비교한다.
- 합계가 다르면 값을 변경하지 않고 weak 경고만 추가하며 허용 오차는 두지 않는다.
  - 의도 : 추출값을 보정하지 않고 관계 불일치를 진단 정보로 남긴다.
4. **medium warning**
- 사채 parser는 `medium_warning`을 직접 만들지 않는다.
  - 의도 : 사채 parser가 실제로 만드는 경고 수준만 문서 계약으로 둔다.
5. **workflow warning code**
- 아래 code는 사채 parser record가 아니라 공통 workflow의 `warnings[]`를 만들 때 warning 문자열에서 변환한다.

| 상황 | `warning_code` |
|---|---|
| 메인 table 누락 | `bond_main_table_missing` |
| 필드 원천 누락 | `source_not_found:<필드명>` |
| 발행목적 합계 불일치 | `bond_funding_purpose_sum_mismatch` |
| 투자자 합계 불일치 | `bond_investor_sum_mismatch` |
| 주입 제목 누락 등 나머지 warning | `parse_warning` |

  - 의도 : 사람이 읽는 warning 문장과 프로그램이 분류에 쓰는 code를 구분한다.
